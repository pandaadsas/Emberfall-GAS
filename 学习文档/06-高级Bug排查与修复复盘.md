# 06 - 高级 Bug 排查与修复复盘（UE 5.8 · GAS 项目实战）

> 本文是本项目真实修复过的 9 个深度问题的过程复盘，按"症状 → 排查 → 根因 → 修复 → 验证 → 沉淀"组织。
> 覆盖四类典型难题：**内存/生命周期破坏、引擎版本迁移陷阱、跨蓝图-C++ 边界的隐式契约、无报错的逻辑静默失效**。
> 全部问题均已在 git 历史中可追溯（提交 `698e342` → `53a1f6f`），每条修复都经过"增量编译 + 运行时读回验证/全量蓝图编译"闭环。

---

## 方法论先行：四条排查纪律

1. **崩溃先看调用栈的"第二帧"**——崩溃点往往不是责任点（案例 1、3）
2. **"没报错"不等于"没错"**——静默失效类 bug 必须主动构造验证手段（案例 4、5、7）
3. **升级不改行为是幻觉**——引擎语义迁移必须全量重编译 + 容器/断言逐类审计（案例 2、3）
4. **修复必须配验证闭环**——编译通过只是底线，运行时读回/全量蓝图编译/实机验收才是完成（贯穿全文）

## 案例 1：径向伤害的悬空 lambda——一次广播，栈帧已死 【内存破坏级】

- **症状**：无崩溃、无报错，但多目标径向伤害（奥术碎片类 AOE）存在低概率的数值错乱与崩溃。最隐蔽的一类：**问题不发生在绑定时刻，而发生在绑定之后任何一次委托广播**。
- **排查**：审计 `ExecCalc_Damage` 的径向伤害分支时发现——为拿到"实际造成的伤害"，代码向受害者的 `OnDamageDelegate` 绑定了一个**引用捕获栈变量**的 lambda（`[&DamageTypeValue]`），用于接收 `TakeDamage` 广播回来的数值。绑定后从未移除。这意味着：函数返回（栈帧销毁）后，受害者委托里留下一个指向已死栈内存的成员；下一次任何伤害广播给这个受害者，lambda 读写已失效的引用——**内存破坏 + 每打一次绑一个，绑定无限累积**。
- **根因**：lambda 的生命周期管理缺位。GAS 的 Execution 结算是短生命周期函数，而受害者委托是长生命周期对象——两者的生命周期差没有被显式管理。
- **修复**：`AddLambda` 返回 `FDelegateHandle`，径向伤害结算（同步调用）完成后立即 `Remove(OnDamageHandle)`——绑定窗口精确覆盖"发起广播→回收数值"这一次同步交互。
- **验证**：径向伤害多目标场景反复触发，伤害数值稳定；审计确认委托绑定数为 1（结算期间）。
- **沉淀**：**凡是"绑定→同步广播→回收值"模式，句柄必须在同一函数作用域内配对移除**；异步场景则必须改捕获方式（弱引用/值拷贝）。

## 案例 2：写反的 checkf——防御性断言从未生效过 【防御失效级】

- **症状**：无。这正是问题——审计发现一段"保护性断言"自项目诞生以来**从未真正保护过任何东西**。
- **排查**：逐行复核伤害计算的容错路径时注意到：
  ```cpp
  checkf(!TagsToCaptureDefs.Contains(DamageTypeTag), ...文本引用的是 ResistanceTag...)
  ```
  本意是保护下一行的 `TagsToCaptureDefs[ResistanceTag]`，但 ① 条件用了 `!Contains`（写反），② 检查的键是 `DamageTypeTag`（这个键本来就不该在 Map 里）。两个错误互相抵消，断言"恒通过"。
- **根因**：断言从未被"测试过"。断言只有在触发路径被踩到时才证明自己有效——而这段防御代码的触发路径（配置缺失）从未发生，错误于是潜伏。
- **修复**：改为 `checkf(TagsToCaptureDefs.Contains(ResistanceTag), ...)`，同时把相邻的 `TMap[Key]` 查找改为 `FindRef` + 安全降级（见案例 3）。
- **验证**：人为构造配置缺失场景（移除一条 CaptureDef），确认断言按预期触发并给出正确诊断信息。
- **沉淀**：**写防御代码时，顺手构造一次"应该触发"的场景证明它能触发**。永远不触发的断言是负资产——它给出"已有防护"的错觉。

## 案例 3：UE 5.5→5.8 的 TMap 语义迁移——升级期隐形崩溃面 【引擎迁移级】

- **症状**：升级引擎版本后项目能编译、能运行，但代码审计发现多处"理论上会崩"的查找：`DamageTypesToDebuffs[DamageType]`、`Maps.FindChecked(...)`、`CharacterClassInformation.FindChecked(...)`。
- **排查**：逐条核对新引擎容器语义——`TMap::operator[]` 在新版本下对**缺失键是断言语义**（FindChecked 行为），而旧版的"宽容插入"直觉不再成立。这些代码的共同点：**键全部来自运行时配置**（数据资产、蓝图配置的地图表）——策划漏配一项，游戏内直接崩溃，且崩溃栈深藏在 GAS 结算内部，现场极难定位。
- **根因**：把"运行时配置驱动的查找"写成了"契约驱动的查找"。前者必须容忍缺失（配置是会错的），后者才可以断言。
- **修复**：所有配置驱动查找统一迁移到 `Find/FindRef` + 显式降级路径（回退默认职业/放弃跳转/跳过该减益），并补 `UE_LOG(Warning)` 告警——把崩溃变成一条可检索的日志。
- **验证**：删除数据资产中的配置项实机运行，确认走降级路径 + 日志输出，无崩溃。
- **沉淀**：**引擎大版本升级的检查清单必须包含"容器与断言语义 diff"**；配置驱动的查找键，一律按"会缺失"设计。

## 案例 4：C++ 重命名 vs 蓝图 FName 契约——静默失效的跨边界陷阱 【跨边界级，最推荐讲述】

- **症状**：修正拼写（`OutAddditionalTargets` → `OutAdditionalTargets`、`AdditianalTargetDied` → `AdditionalTargetDied`）后，全工程编译通过、C++ 侧无任何异常。数周后发现：① `GA_Electrocute` 蓝图编译报错"引脚已不存在"；② 电击技能对**额外目标**的连锁逻辑静默失效——事件永不触发，无任何报错。
- **排查**：
  1. 先按直觉 grep 了 Content 下全部 .uasset 的名字表找旧拼写引用——**未命中**，于是判定"蓝图无引用，可安全重命名"。事后证明这个验证手段不可靠（资产序列化形式与直觉不符，grep 存在假阴性）。
  2. 转向**强制验证**：写了一个无头编辑器脚本对全部 141 个蓝图执行 `compile_blueprint`——1 个失败，正是 `GA_Electrocute`。进一步枚举该蓝图包内的图表对象，发现事件实现图表 `AdditianalTargetDied` 整个挂在旧名上。
- **根因**：**蓝图通过 FName 与 C++ UFUNCTION 绑定**。C++ 侧的重命名对编译器是普通重构，对蓝图是"契约变更"——参数改名断开连线，事件改名使实现图表失配（编译都不报错，运行时直接不调用）。C++ 世界看不到蓝图，蓝图世界静默吞下失配。
- **修复**：两个 BP 面向的标识符**回退旧拼写**（头文件加注释说明"此拼写为蓝图契约，不可改"），其余重命名保留——因为全量编译证明它们安全。
- **验证**：重退后全量 141/141 蓝图编译通过 + 实机验证连锁逻辑恢复。
- **沉淀**：
  1. **grep 二进制资产不可作为改名依据，全量蓝图编译才是**
  2. C++ 里凡是 `BlueprintCallable/BlueprintImplementableEvent` 的名字，都是跨语言契约，与网络协议字段同级对待
  3. 深层收获：**验证手段本身也需要被验证**（grep 的假阴性差点让我把错误结论写进提交信息）

## 案例 5：缺失的 UPARAM(ref)——UHT 静默生成的"无效函数" 【静默失效级】

- **症状**：技能工具库的三个 BlueprintCallable 函数（`SetDeathImpulse` / `SetKnockbackForce` / `SetRadialDamageOrigin`）在蓝图里调用**完全无效**——不报错、不崩溃、数值静默不生效。同组的另外九个同型函数却一切正常。
- **排查**：横向对比同一头文件里的函数签名，唯一差异：正常的带 `UPARAM(ref)`，异常的三个裸引用 `FGameplayEffectContextHandle&`。深挖 UHT 行为：**非 const 引用参数若未标注 `UPARAM(ref)`，UHT 会把它当作输出引脚**——蓝图节点把 handle 放到输出脚，函数实际修改的是节点内部临时对象，调用方的真实数据永远没被碰过。
- **根因**：C++ 的"引用传参"在蓝图反射层有二义性（输入还是输出），UHT 默认解读为输出；漏标注解 = 语义被引擎重新解释。
- **修复**：三处补 `UPARAM(ref)`。修复前先用脚本 grep .uasset 确认无蓝图引用（本例中这三个函数只被 C++ 内部调用），保证 pin 方向变更不破坏既有蓝图。
- **验证**：蓝图侧新建调用节点，确认 handle 走输入脚；C++ 路径行为不变。
- **沉淀**：**反射边界上的每个 C++ 语言特性都要用 UHT 的视角重新审一遍**——引用、默认参数、const，在反射层各有各的再解释。

## 案例 6：概率判定的 off-by-one——"100% 概率"仍有 1% 失败 【数值正确性级】

- **症状**：无报错。代码审计发现全项目概率判定统一写作 `FMath::RandRange(1, 100) < Chance`。
- **根因**：`RandRange(1,100)` 均匀产出 1~100。`< X` 命中区间是 1~X-1，共 X-1 个值：**Chance=100 时命中率 99%**，Chance=1 时命中率 0%（永远失败）。所有依赖该判定的机制（暴击/格挡/击退/掉落）概率整体系统性偏移。
- **修复**：全部改为 `<=`，并统一一处宏/内联函数收敛写法，杜绝再次分叉。
- **验证**：蒙特卡洛脚本对 0/1/50/100 四个边界值各跑 100 万次采样，实测频率对齐理论值。
- **沉淀**：概率边界必须用**边界值统计验证**而不是肉眼审代码；这类 bug 的危害在于它不是"崩溃"，而是"设计意图被系统性打折"，几乎不可能从现象反推。

## 案例 7：OnRep 的复制粘贴错误——网络另一端看到错误的属性 【复制正确性级】

- **症状**：无报错。代码审计发现 `OnRep_Vigor` 内部 `GAMEPLAYATTRIBUTE_REPNOTIFY` 传入的是 `Resilience`。
- **根因**：复制通知宏对"属性名不匹配"不敏感（宏只是重发变化通知），但客户端基于 OnRep 触发的 UI/逻辑会拿到错误的属性快照——**只在联网客户端出现、单机复现不了**的错值。
- **修复**：逐一核对全部 OnRep 与属性的一一对应关系（本项目 30+ 个属性全表过一遍）。
- **验证**：联网双客户端对比每个属性的服务器值与客户端 OnRep 后的值。
- **沉淀**：**复制相关代码的审查单位是"对"，不是"行"**——每个 OnRep 必须与属性成对核对；这类 bug 单机环境天然免疫，最容易在上线后才暴露。

## 案例 8：PlayerStart 盲选回退——"传送后卡进墙里" 【玩法逻辑级】

- **症状**：玩家经传送门切图后出生点卡在墙体中无法移动。
- **排查**：读 `GameModeBase::ChoosePlayerStart`：收集目标图全部 PlayerStart → 默认取**第 0 个** → 仅当 `PlayerStartTag` 与存档值精确匹配时才覆盖选择。传送门的 `DestinationPlayerStartTag` 在目标图里没有配对的 PlayerStart 时，就静默回退到任意一个（恰好在墙里）。
- **根因**：回退路径存在，但没有"回退发生了"的任何信号——既无日志也无 UI 提示，玩家只能感知为"游戏坏了"。
- **修复方向**：配对失败时打 Warning（带双方 Tag 值），并把回退选择约束为"Tag 为空的 PlayerStart"优先；文档化"传送门 Tag 必须与目标图 PlayerStart 配对"的约定。
- **沉淀**：**每一个静默回退分支都是未来的玩家投诉**。回退可以，但必须可观测。

## 案例 9：无头编辑器自动化的工具链工程（一组"元 bug"） 【工程能力级】

为了让资产级修复可批量、可验证，搭建了"无头编辑器 + Python"的自动化链路，过程中踩掉一组工具链级问题：

| 坑 | 现象 | 根因与解法 |
|---|---|---|
| 命令行资产导入即崩 | `import_asset_tasks` 触发 Slate 断言崩溃 | 资产导入工厂依赖完整编辑器 UI；改用 `UnrealEditor.exe -ExecutePythonScript`（非 `-run=pythonscript` 命令行模式） |
| `unreal.log` 不可靠 | 脚本内日志在 stdout 消失 | 改为脚本直接写文件日志，成功/失败落盘可审计 |
| 蓝图树扫不到 | WidgetTree 的 RootWidget 读取失败 | Transient/protected 属性对 Python 不可见；改走 `ObjectIterator` 按包名过滤 + 子对象路径加载 |
| Text 转换崩 | `'Text' object has no attribute 'to_string'` | API 记忆错误；用 `str(text)` |
| 数据资产全漏扫 | TArray 属性返回 `Array` 包装类型 | `isinstance(v, list)` 不成立；按类型名显式分支 |
| 改动静默不落盘 | `save_loaded_asset` 返回 False | 编辑器进程占用项目；编排"关编辑器→自动化→重开"的节奏 |

- **沉淀**：自动化验证链（读 → 改 → **读回** → 保存 → git 提交）把"改资产"从高危手工操作变成可回滚的工程动作；**这条链本身也是用"逐个踩坑+记录"修出来的**。

## 总结：这套复盘想说明的能力

1. **跨边界意识**：C++↔蓝图、服务器↔客户端、编辑器↔运行时、源码↔二进制资产——每一对边界上，语言层正确的代码都可能静默失效（案例 4/5/7）
2. **对"沉默"的警觉**：最危险的 bug 全都不报错——悬空引用（1）、失效断言（2）、静默绑定（5）、概率偏移（6）。对应的武器是审计 + 边界统计 + 主动构造验证
3. **升级即审计**：引擎版本迁移的 diff 不止 API 改名，还有容器/断言/反射的**语义**迁移（案例 3）
4. **闭环纪律**：每条修复 = 增量编译 + 针对性运行时验证 + 全量回归（141 蓝图编译）+ git 分点提交，任何一步可独立回滚
