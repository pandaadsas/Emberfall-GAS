## 一、项目性能现状画像（基于代码审计，非实测）

### 1.1 内容与负载特征
- 场景资产为课程级体量：单张战斗图 + 少量角色/特效，**GPU 压力天然不高**
- 真正的隐患集中在**游戏线程的每帧固定开销**与**运行时对象分配**上（详见 01 文档逐条清单）
- UI 层为全量广播模型：任何属性/技能状态变化都会刷新整块面板
- AI 索敌使用每 Tick 全场景 Actor 扫描（`BTService_FindNearestPlayer`）

### 1.2 帧率现状估算（中端桌面机 1080p，如 RTX 3060 / 6 核 CPU）

| 场景 | 估算现状 | 主要约束 | 依据 |
|---|---|---|---|
| 主菜单/读档（UI 静态） | 120–200 FPS | GPU 几乎空闲 | 无 3D 负载 |
| 第一张图·漫游（无战斗） | 110–160 FPS | GPU（场景渲染）为主 | 内容轻量 |
| 第一张图·战斗（技能特效+5~10 敌人） | **90–144 FPS** | CPU/GPU 交替，技能爆发帧掉至 60–90 | Niagara 特效 + 每帧 AI 查询 + 伤害跳字组件分配 |

> ⚠️ 以上为假设区间。当前内容量下帧率"看起来不差"，**优化的真正价值是为内容扩容预留帧预算**：
> 乐观预期下，同等画面档位可获得 **30–50% 的帧预算余量**（约等于"同样的帧率能多塞一倍的怪和特效"），具体论证见 01 文档各条目的收益估算。

### 1.3 网络现状
- 默认单机；代码已具备 Listen Server 联机骨架（GAS 复制、TargetData 预测键、Server RPC）
- 联机化后**可预见的问题清单**已就位：30+ 属性全量 `COND_None` 复制、全量状态广播、无相关性裁剪、无延迟补偿——逐条见 02 文档

## 三、测量方法学（落地任何优化前先做）

所有理论数字必须用以下流程校准，**先测基线，再改，再对比**：

1. **帧内耗时拆分**：`stat unit`（Game/GPU/Draw 总览）→ 判断 CPU-bound 还是 GPU-bound；
   `stat game`（游戏线程明细）、`stat gpu`（GPU 明细）定位到子系统
2. **微分析**：Unreal Insights（`-trace=cpu,gpu,net`）录制战斗 60 秒，看 Timeline 上的分配、Trace、Widget 刷新热点
3. **网络基线**：`stat net`（流量）、`net PktLag=100` 模拟延迟；Listen Server 下 2 客户端连接测稳态 KB/s
4. **对照纪律**：一次只改一项 → 同场景同机位录 60s → 对比 P50/P1 帧率与 Insights 热点；
   建议建一张固定的"基准地图"（固定敌人数量/特效触发脚本），避免场景差异污染数据
5. **资产规模基线**：`stat scenerendering`、GPU Profiler（Ctrl+Shift+,）逐 Pass 记录
