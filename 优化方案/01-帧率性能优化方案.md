# 01 - 帧率性能优化方案（渲染 + 游戏线程）

> **纯方案文档，不含代码改动。** 每条按"现状（代码锚点）→ 方案方向 → 理论收益（含假设）→ 成本/风险 → 验证手段"组织。
> 收益数字为理论估算：以中端桌面机（6 核 CPU / RTX 3060 级 / 1080p）、第一张图 5–10 敌人战斗场景为假设基准（基线 ≈ 90–144 FPS，见 00 文档）。
> 收益不可叠加简单相加——Amdahl 定律：单项收益受其在帧耗时中的占比上限约束。

---

## 一、瓶颈假设模型（先立靶子）

帧耗时 = 游戏线程（Game）+ 渲染线程（Render）+ GPU，三者取最大值（流水线并行）。

| 子系统 | 当前估算占比（战斗场景） | 主导因素 |
|---|---|---|
| 游戏线程 | 4–8 ms | AI 每 Tick 全场景查询、每帧鼠标寻迹、伤害跳字组件分配、UI 全量广播、GAS 属性副作用链 |
| 渲染线程 | 1–2 ms | 提交开销为主，场景简单 |
| GPU | 3–6 ms（技能爆发 6–12 ms） | Niagara 特效、动态光、UI 贴合层 |

> 战斗时 Game 与 GPU 接近交替成为瓶颈；**技能爆发瞬间（多目标 AOE + 跳字）是掉帧尖峰的主要来源**——这是优化重点对准"分配与全量刷新"的原因。

---

## 二、游戏线程优化清单

### 2.1 AI 索敌：每 Tick 全场景扫描 → 事件驱动 + 降频 【P0】

- **现状**：`BTService_FindNearestPlayer::TickNode` 每帧对全场景 `GetAllActorsWithTag`（O(场景 Actor 数) 线性扫描 + Tag 匹配），每个敌人 AI 各跑一份。10 敌人 × 60FPS = 每秒 600 次全场景扫描。
- **方案方向**（三档，任选或组合）：
  1. **降频**：BTService 设 `NextRequiredInterval = 0.1~0.2s`（视野类服务对 100ms 精度完全不敏感）
  2. **注册表缓存**：维护一个"存活玩家列表"注册表（玩家 OnSpawn/OnDeath 时增删），AI 只查表不扫场景 → O(N_player)
  3. **完全事件驱动**：玩家位置用球形触发器/Team 索引聚合，AI 订阅变更事件，零 Tick 查询
- **理论收益**：该服务当前估算占游戏线程 0.5–2ms（随敌人数线性）。10 敌场景下降频到 5Hz 即 **−80~95% 该项开销 ≈ 释放 0.4–1.6ms/帧**；事件驱动可逼近 0。
- **成本/风险**：低。降频引入 ≤200ms 的目标切换延迟（战斗中无感）；注册表需处理玩家死亡/断线的移除时机。
- **验证**：Unreal Insights 对比 `BTService` 时间片；`stat game` 观察 AI 分类耗时。

### 2.2 伤害跳字：每次 NewObject 组件 → 组件对象池 【P0】

- **现状**：`DuraPlayerController::ShowDamageNumber` 每次受伤 `NewObject<UDamageTextComponent>` + RegisterComponent + 动画结束销毁。AOE 命中 8 个目标 = 一帧内 8 次组件对象分配 + 8 次挂载 + 稍后 8 次销毁——**帧尖峰的直接来源**。
- **方案方向**：
  1. **组件池**：预分配 N 个跳字组件，用完归还（隐藏 + 移除绑定 + 重置状态），命中时取用
  2. **进阶（更省）**：跳字改为**单一 UI 管理器 + 屏幕坐标列表**（UMG 一个 Retainer/画布画所有跳字，数据驱动），彻底消灭 Actor 组件
- **理论收益**：技能爆发帧消除 8–30 次组件生命周期开销，估算 **0.3–1.5ms 尖峰削减**；GC 压力显著下降（对象 churn 是 GC 尖峰主因之一）。
- **成本/风险**：低-中。池需要上限策略（超出上限丢弃最旧跳字）；方案 2 需要重做跳字定位逻辑（世界坐标→屏幕坐标投影）。
- **验证**：`stat obj`（对象数稳定性）、Insights 的 GC 事件、爆发帧 P1 帧时间对比。

### 2.3 鼠标寻迹：每 Tick 线程 traced → 降频 + 按需 【P0】

- **现状**：`DuraPlayerController::PlayerTick` 每 Tick `MouseTrace()`（GetHitResultUnderCursor）+ `AutoRun` + `UpdateMagicCircleLocation`。寻迹结果只服务于**光标高亮与点击目标**，人眼对 60→20Hz 的光标更新完全无感。
- **方案方向**：Tick 内累计 dt，≥1/20s 才执行一次 MouseTrace；魔法阵位置更新可单独保持 60Hz（便宜）。更进一步：高亮状态变化时才调用高亮接口（当前每帧重复调用 Highlight）。
- **理论收益**：游戏线程 **−0.2–0.8ms/帧**（视场景射线复杂度）；同时减少物理场景查询的渲染线程同步点。
- **成本/风险**：极低。高亮在快速划过敌人时最多延迟 50ms。
- **验证**：Insights 对比 `LineTrace` 相关时间片。

### 2.4 动态 GameplayEffect：每次 NewObject → 模板缓存 【P2】

- **现状**：`DuraAttributeSet::Debuff()` 每次施加减益都 `NewObject<UGameplayEffect>(GetTransientPackage())` 动态拼一个 GE（持续/周期/标签/Modifier 全套装配）。
- **方案方向**：按 DamageType 预构建 4 个 GE 模板（CDO 化或数据资产），运行时仅通过 SetByCaller 改数值；或缓存已构建模板的克隆。
- **理论收益**：单次施加省一次 UObject 装配；Burn 这类高频周期减益在多人/多怪下**累积可观**（估算战斗帧 0.1–0.5ms + GC 减负）。属于"爆发平滑度"优化。
- **成本/风险**：中。模板化后 Stack/周期语义要与现行为逐一比对（减益叠加规则曾在本项目修过 bug，回归测试必须覆盖）。
- **验证**：减益施加路径的 Insights 计时 + 玩法回归（灼烧/眩晕/叠加次数）。

### 2.5 UI：全量广播 → 差量刷新 + Invalidation 【P1】

- **现状**：WidgetController 以"广播整个 Info 结构体"为粒度（`AbilityInfoDelegate.Broadcast(Info)`、属性值每次变化全面板刷新）。UMG 默认每帧全量 OnPaint；无 Invalidation Panel / Retainer。
- **方案方向**：
  1. 广播携带变化字段（或由 UI 端做脏标记短路）
  2. 属性菜单/技能菜单套 **Invalidation Panel**（静态区域缓存为贴图）；数值变化才重绘
  3. 血条/蓝球这类高频控件独立 Retainer 并限制刷新率（30Hz 足够）
- **理论收益**：战斗帧 **+3–8%**（UI OnPaint 占比取决于面板打开频率；Overlay 常驻元素是主要受益者），毛刺（spike）减少比均值收益更有感。
- **成本/风险**：中。Invalidation 对含动效的子树无效（需隔离动效元素）；Retainer 有半帧延迟。
- **验证**：`stat slate`（OnPaint/PrePass 耗时）、Insights Slate 时间线。

### 2.6 GAS 执行路径：捕获定义与副作用链 【P2】

- **现状**：`ExecCalc_Damage` 每次结算构建 `TagsToCaptureDefs` TMap（10+ 项插入）；`DuraDamageStatics` 静态单例已是好实践；属性 PostGameplayEffectExecute 链路串行触发 XP/升级/跳字/掉落。
- **方案方向**：TMap 构建移到构造期一次性完成（键集合静态）；结算内只做查找。进一步可用 **AttributeSet 的 Replication/副作用批处理**（同一帧多次属性变化合并广播一次 UI 刷新）。
- **理论收益**：单次伤害结算 −5–15% 结算耗时；多目标 AOE（ExecCalc 被并发调用 N 次）时收益 ×N。
- **成本/风险**：低。纯等价重构，注意 Tag→Def 映射的静态初始化时机（模块加载后、首次结算前）。
- **验证**：Insights 计时 Execute_Implementation 均值/P95。

### 2.7 Tick 纪律审计（系统性） 【P1】

- **方向**：全项目审计 `PrimaryActorTick.bCanEverTick = true` 的 Actor 与组件，逐个回答"能否事件化/降频"：弹丸 Tick（直线弹道可改 ProjectileMovement 组件接管，物理子步进）、存档点/传送门（纯 Overlap 驱动，本就无 Tick ✓）、魔法阵（低频）。
- **理论收益**：每个消灭的 Tick 是**固定常量收益**，与内容量成正比——内容扩容时收益自动放大。
- **成本/风险**：低；逐个验证即可。
- **验证**：`stat dumpframe` / Insights 列出所有 Tick 条目及耗时排序。

## 三、渲染与 GPU 优化清单

### 3.1 基础项核查（做内容之前先锁对） 【P0】

- **方向**：确认以下项目的当前档位并记录（这些是"档位错误"级别的收益）：
  - 阴影：动态光数量、级联数、`r.Shadow.MaxCSMResolution`
  - 抗锯齿：TSR 档位（Performance/Balanced/Quality 对帧率影响 15–30%）
  - Lumen（若启用）：Final Gather 质量、Lumen Scene 细节
  - 后处理：Screen Space 反射/环境光遮蔽档位
- **理论收益**：档位各降一级通常 **GPU −10–25%**，视觉损失在小屏幕/动态画面下不敏感。
- **验证**：GPU Profiler 逐 Pass 前后对比。

### 3.2 Niagara 特效：Scalability + Significance Manager 【P2】

- **现状**：技能特效（火弹/爆裂/电击光束/奥术碎片）在技能爆发时同屏多实例；未见按距离/重要性的效果降级。
- **方案方向**：
  1. 每个特效资产设置 **Effect Type + Scalability 档位**（远距离自动裁剪粒子/关光照）
  2. 接入 **Significance Manager**：按屏幕占比+距离打分，低分实例降 Tick 频率/粒子预算/关掉 GPU 仿真
  3. 伤害类瞬时特效共享粒子池（同模板实例化复用）
- **理论收益**：技能爆发 GPU **+15–30%**；多怪混战场景（同屏 5+ 特效实例）收益上限更高。
- **成本/风险**：中。Significance 需要注册/评分代码路径（一处通用实现，特效资产逐个挂 Effect Type）。
- **验证**：`Niagara.Debugger`（实例预算可视化）+ 爆发帧 GPU Profiler 对比。

### 3.3 角色与武器渲染 【P3】

- **方向**：敌人多实例同屏时的材质复杂度审计（半透明排序开销、overdraw）；贴花（魔法阵）改用 DecalComponent 池或投影材质降采样；远处敌人 LOD 生效验证（骨架网格 LOD + Anim 加距离剔除）。
- **理论收益**：混战场景 GPU +5–15%；overdraw 是俯视角 UI 遮挡大时的隐性杀手。
- **验证**：`stat scenerendering`（draw call / 三角形 / 半透明占比）+ Quad Overdraw 视图。

## 四、内存与分配（GC 健康度） 【P1】

- **现状盘点**：跳字组件（2.2）、动态 GE（2.4）、`FString::Printf` 技能描述每次悬停重建、Broadcast 的结构体拷贝——都是**稳态小分配**，单次不痛，累积成 GC 尖峰（表现为"玩着玩着突然掉一帧"）。
- **方案方向**：跳字/GE 走池化（见上）；技能描述按 (Ability, Level) 缓存；热路径 FString 改 FText 惰性构建或字符复用；开启增量 GC（5.8 默认）并确认无长阻塞。
- **理论收益**：GC 尖峰从"可感知掉帧（10–30ms）"降到 <5ms；平均帧率影响小但**1% Low FPS 显著改善**（流畅度体感）。
- **验证**：Insights GC 时间线、`stat obj`、`memreport -full` 前后对比。

## 五、预期总体收益（理论）

| 指标 | 现状估算 | 优化后估算 | 条件 |
|---|---|---|---|
| 战斗平均帧（当前内容量） | 90–144 | **140–200+** | P0+P1 落地，GPU 档位核查 |
| 技能爆发帧（P1 帧时间） | 60–90 | **100–144** | 对象池 + Niagara significance |
| 1% Low FPS | 45–70 | **80–120** | GC 优化（第四节的池化+缓存） |
| 帧预算余量（同帧率下可加内容） | 基准 | **+30–50% 敌人/特效规模** | 全清单落地 |
| 10 敌 × 60FPS 场景的 AI 索敌总开销 | 30–120ms/s | **<5ms/s** | 事件驱动方案 |

> 再强调：以上均为**方向性理论估算**，精确数字以 00 文档第三节的实测流程为准。优化的正确姿势是"测基线 → 单项改 → 对照验证"，本文档提供的是候选清单与优先级，不是一次性的施工许可。
