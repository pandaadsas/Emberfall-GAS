# 02 - 网络同步优化方案（调优清单 + 架构演进路线）

> **纯方案文档，不含代码改动。** 分两部分：
> **A 部分**针对现有代码——一旦以 Listen Server 联机即可受益的调优清单；
> **B 部分**是从单机 demo 走向"商业联机"的架构演进路线（大方向与决策依据，不展开实现）。
> 带宽/延迟数字均为理论估算，标注了假设；实测方法见 00 文档第三节。

## 〇、现状网络画像（代码审计结论）

| 维度 | 现状 | 评价 |
|---|---|---|

## A 部分 · 现有代码调优清单（联机前必做）

### A1. 属性复制条件分类 【带宽收益最大的一项】

- **现状**：`DOREPLIFETIME_CONDITION_NOTIFY(UDuraAttributeSet, X, COND_None, REPNOTIFY_Always)` × 30+。`COND_None` = 每个属性变化都复制给**所有**连接。敌人的护甲穿透、其他玩家的 XP 曲线……全是无用流量。
- **方案方向**：
  1. **按"谁需要知道"分类**：
     - 敌人血量/等级 → 所有客户端（战斗 UI 需要）→ 保留 COND_None
     - 玩家 XP/技能点/属性点 → **COND_OwnerOnly**（只有本人 UI 需要）
     - 敌人抗性/暴击率等"结算用"属性 → 服务器结算用，**客户端根本不需要复制** → `COND_None` 改为不复制（DOREPLIFETIME_CONDITION 删除或 `SetIsReplicatedByDefault(false)` 的独立 AttributeSet 拆分）
  2. **REPNOTIFY 策略复核**：`REPNOTIFY_Always` 用于"值相同也要触发 OnRep"的场景（如数值回满）；普通变化改 `REPNOTIFY_OnChanged` 减少无效回调
  3. **进阶：属性拆分 AttributeSet**——把"结算专用属性"（服务器 only）与"展示属性"拆成两个组件/集合，从源头不复制前者
- **理论收益**：假设 8 玩家 + 30 敌人：现状属性流量 100% 广播；分类后估算**稳态带宽 −70~90%**（血量/蓝量变化才是真正需要广播的少数派）。
- **成本/风险**：中。逐属性判断"谁需要"，漏判会造成 UI 缺数据（回归点：每个 UI 绑定字段逐一验证）。
- **验证**：`stat net`、`net.CallRPCTally`、两客户端连接观察各属性 OnRep 触发计数（可临时打日志计数后移除）。

### A2. Push Model 复制（服务器主动推送变化）

- **现状**：默认复制模型下，服务器每 Tick 对比全部复制属性找变化（轮询式，属性越多 CPU 越贵）。
- **方案方向**：UE5 的 `Push Model`（`DOREPLIFETIME_WITH_PARAMS_FAST` + 属性 Setter 里 `MARK_PROPERTY_DIRTY_FROM_NAME`）。GAS 的属性 Setter（`SetHealth` 等）是集中收口点，改动面收敛。
- **理论收益**：服务器复制对比开销 **−60~90%**（从 O(属性总数×频率) 降到 O(实际变化)）；带宽数值不变，但**服务器 CPU 随人数的扩张曲线显著变缓**——这是"能带多少同图玩家"的容量指标。
- **成本/风险**：中。漏标 DIRTY 会导致属性不同步（静默 bug），需要逐一核对所有写入路径（含 ExecCalc 的属性修改路径——注意 ExecCalc 走引擎内部路径，需确认其 Push 行为）。
- **验证**：`stat net` + `net.RepGraph.*`/push model 调试计数；构造"属性变化压力测试"（脚本刷属性）对比服务器帧耗时。

### A3. 复制量化与频率

- **方向**：float 属性全按 32bit 全精度复制。对"展示用"属性（血量、蓝球百分比）启用**量化**（`DOREPLIFETIME_CONDITION_NOTIFY` + `CPP_Default_*` 或属性的 Quantized 配置）压缩到 8/16bit；低频属性（经验曲线参数）合并进低频更新通道。
- **理论收益**：展示属性网络占用 −50~75%；配合 A1 后稳态带宽可达 <10 KB/s/客户端 量级（估算）。
- **成本/风险**：中。量化精度要在 UI 显示精度内（血量显示整数值 16bit 足够）。

### A4. RPC 纪律

- **现状线索**：`ClientUpdateAbilityStatus`（技能状态变更即时推送）这类 RPC 在批量解锁时会连发；伤害跳字走 `Client RPC`（`ShowDamageNumber`）逐次发送。
- **方案方向**：
  1. **合并/节流**：同帧多条状态变更合并为一条数组 RPC
  2. **可靠性降级**：跳字/特效类 RPC 用不可靠通道（丢失可容忍，避免可靠队列拥塞反压）
  3. **带宽守门**：给"装饰性 RPC"（跳字、消融特效）设总量上限，超限丢弃
- **理论收益**：混战场景 RPC 流量峰值 **−30~60%**；可靠通道拥塞消除后，关键同步（施法确认）延迟抖动改善。
- **验证**：`net.Reliable.Debug`、`stat net` 的 RPC 分类计数。

### A5. 相关性与休眠（Actor 级）

- **现状**：存档点/传送门/装饰盘、出生区域等静态 Actor 默认全时相关；敌人死亡后 LifeSpan 期间仍参与复制。
- **方案方向**：
  1. 静态 Actor（存档点/传送门/效果 Actor）设 **`DORM_Initial`→唤醒→`DORM_DormantAll`**（Overlap 时才唤醒）
  2. 敌人配置 **NetCullDistance**（俯视角相机下 4000–6000 uu 足够，超出不复制）
  3. `NetUpdateFrequency` 分级：玩家 30–60Hz、敌人 10–20Hz、静态物接近 0
- **理论收益**：参与复制评估的 Actor 数量下降一个数量级；服务器每帧复制遍历成本 **−50~80%**；带宽同步下降。
- **成本/风险**：低-中。Dormancy 唤醒时机要覆盖所有交互入口；Cull 距离要大于俯视角可视范围（相机看得见的必须复制）。
- **验证**：`stat net actor`（相关 actor 计数）、`net.RepDebugger`。

### A6. GameplayCue 与特效的网络策略

- **方向**：伤害/命中类 Cue 走 multicast 不可靠（丢失无感）；持续类（灼烧光环）用静态 Cue（附着在 GE 上自动管理）；同帧多目标命中合并 Cue 参数（`GameplayCueParameters` 聚合）。
- **理论收益**：AOE 帧的 Cue 包数量 −50%+；不可靠化后不占可靠窗口。
- **验证**：`net.GameplayCueDebug`、抓包/`stat net` 对比。

## B 部分 · 架构演进路线（单机 demo → 商业联机）

> 按阶段推进，每阶段独立可交付。不建议跳级——下一阶段的收益依赖上一阶段的地基。

### B1. 阶段一：专用服务器（Dedicated Server）基建 【决策门槛：确定要做多人】

- **内容**：Dedicated Server 目标构建（打包含 Server Target）；GameMode/HUD/UI 的"服务器无头"路径审计（当前 HUD/WidgetController 在服务器上也会构建，DS 上应短路）；存档系统从 GameMode 内存态迁到可持久化（DS 是无状态的）；所有"UI 直接读世界"的路径改为事件订阅。
- **收益**：反作弊底线、7×24 稳定性、玩家规模能力的**前提条件**。
- **量级**：大。涉及架构性拆分，建议排在所有玩法内容稳定之后。
- **验收信号**：DS 构建跑通同图战斗，客户端 UI 数据完整。

### B2. 阶段二：移动与手感——预测参数调优 → 下一代网络移动评估

- **内容**：
  1. **CMC 参数调优**（低成本，先做）：`NetworkMaxSmoothUpdateDistance`、`NetworkSimulatedSmoothLocationTime`、`ListenServerNetworkSimulatedSmoothLocationTime` 等——模拟端（Simulated Proxy）平滑参数直接决定其他玩家移动的观感
  2. **评估 Mover 2.0 / Network Prediction Plugin**（UE5 新网络移动体系）：插画式插值 + 独立于 CMC 的预测框架。评估点：项目移动逻辑简单（点地移动+WASD），CMC 现有能力大概率够用；Mover 的收益在"非标准移动"（抓钩/载具/时间操控）出现时才显著
- **收益**：高延迟下"别人家的角色"移动平滑质变；为复杂移动玩法铺路。
- **量级**：调优小；换框架很大（建议观望到引擎正式定版）。

### B3. 阶段三：复制规模化——Replication Graph 或 Iris

- **决策依据**：
  - 规模预估 <32 人同图：A 部分调优 + Replication Graph 足够
  - 目标是大世界/MMO 式规模：直接评估 **Iris**（5.x 新复制栈，UE5.7+ 逐步可用；5.8 下仍需验证生产成熟度）
- **Replication Graph 核心思路**（高级概述）：把"每 Actor 独立判定相关性"改为**空间网格节点 + 持久化连接信息**——玩家相关集合由图节点预计算，服务器不再逐 Actor 轮询。敌人按网格分桶、玩家列表常驻节点、Dormancy 配合，服务器 CPU 与带宽随人数的增长曲线由线性变平缓。
- **理论收益**：同图人数容量 **×5–10**（乐观估算）；带宽在人多的场景不随人数线性爆炸。
- **量级**：很大（复制体系整体迁移），且需要重写 UReplicationGraph 子类。**前置条件**：A 部分全部落地（垃圾流量会污染图的收益）。

### B4. 阶段四：延迟补偿（Server-side Rewind）

- **问题**：俯视角 + 弹道/即时命中技能下，客户端看到的敌人在"过去"，服务器判定在"现在"——高延迟玩家永远打空。
- **方向**：服务器保存敌人最近 N 帧的历史位置 → 技能命中判定时回溯到"攻击者当时的视角帧"做判定（`Server Side Rewind`）；配合命中前移（Forward Prediction）。
- **理论收益**：100ms 延迟下命中率恢复到接近本地体感——**竞技公平性质变**。
- **量级**：中-大（历史缓冲 + 判定时机改造 + 作弊边界）。俯视角游戏输入节奏比 FPS 慢，120ms 内体感尚可，可先上 B1~B3 观察是否真的需要。

### B5. UI 数据通道重构（伴随 B1）

- **方向**：当前 WidgetController 直接订阅世界内 ASC——DS 上没有 UI，客户端 ASC 复制时机与 UI 构建时序存在竞态。演进为"UI 只订阅本地 PlayerState/PlayerController 持有的数据模型（MVVM ViewModel 已是现成骨架）"，由复制驱动 ViewModel，UI 与网络彻底解耦。
- **收益**：读档/换图/重连时 UI 不丢状态；联机下界面数据源唯一。
- **量级**：中。本项目已有 MVVM 骨架（ModelViewViewModel 插件已启用），是顺势而为的改造。

## 三、带宽预算估算（假设 8 玩家 + 30 敌人同图）

| 项目 | 未调优估算 | A 部分调优后估算 | 备注 |
|---|---|---|---|
| 属性稳态流量 | 20–60 KB/s/客户端 | **2–8 KB/s/客户端** | A1 分类 + A3 量化 |
| 移动同步 | 8–15 KB/s/客户端 | 8–15 KB/s（CMC 自身已优化） | 与人数线性 |
| RPC（技能/跳字/状态） | 峰值 30–80 KB/s | 峰值 10–30 KB/s | A4 合并+不可靠化 |
| Actor 相关性开销（服务器 CPU） | 基准 | −50~80% | A5 dormancy+cull |
| 初始同步（进图瞬间） | 数 MB | <1 MB | A1 + 按需加载 |

> 数字为构造估算（基于属性数量、复制频率与典型 overhead 的推理），用于比较量级，不是承诺值。实测以两客户端 Listen Server + `stat net` 为准。

## 四、推进建议（一句话版）

1. 联机前先打完 **A 部分清单**（每条独立、风险低、验证便宜）
2. **B1 专用服务器**是分水岭——上它之前先把玩法内容做稳定
3. **B3 复制规模化**只在人数目标 >32 时启动；**Iris** 保持观望
4. 所有阶段共用一条铁律：**先测基线，单项改动，对照验证**（00 文档第三节）
