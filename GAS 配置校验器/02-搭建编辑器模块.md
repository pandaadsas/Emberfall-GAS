# 02 - 搭建编辑器模块

> 「制作过程」第 2 篇：一个 C++ 编辑器工具的"骨架"是怎么搭起来的。涉及 3 个文件：`.uproject`、`Build.cs`、模块入口类。

---

## 1. 先搞懂：为什么工具代码不能写在 Dura 模块里

Dura 是 **Runtime 模块**（游戏运行时的代码），打包游戏时它会被编进游戏包。如果校验器代码写在里面，会带来两个问题：

1. **打包报错或代码泄漏**：`UnrealEd`、`Slate` 这些模块只在编辑器环境存在，Runtime 模块依赖它们直接编不过；就算绕过去，工具代码也会被塞进游戏包。
2. **职责混乱**：游戏逻辑和工具逻辑搅在一起，以后谁都不敢删。

所以 UE 的标准做法是：**工具单独放一个 `Type: "Editor"` 的模块**。它只在你打开编辑器时加载，打包游戏时整个被跳过。

## 2. 动手：三个文件

### 2.1 在 Dura.uproject 里注册模块

在 `Modules` 数组里追加：

```json
{
    "Name": "DuraEditor",
    "Type": "Editor",
    "LoadingPhase": "Default"
}
```

- `"Type": "Editor"`：只在编辑器目标下编译加载，打包游戏自动忽略
- `"LoadingPhase": "Default"`：默认阶段加载就够用（我们要挂菜单，不需要更早的 PostConfigInit 之类）

> **一个隐含的坑**：`.uproject` 里的模块必须能被编译目标（Target）找到。本项目 `DuraEditor.Target.cs` 已经预先存在（空模板，没有 ExtraModuleNames），UE5.8 的 UBT 会自动从 `.uproject` 收集模块，所以 Target 文件不用改。如果你的项目 Target 里显式写了 `ExtraModuleNames`，记得把新模块也加进去。

### 2.2 建 Source/DuraEditor/DuraEditor.Build.cs

`.Build.cs` 是模块的"购物清单"——声明依赖哪些其他模块，UBT 据此配置 include 路径和链接库：

```csharp
public class DuraEditor : ModuleRules
{
    public DuraEditor(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;

        // 公开依赖：头文件里 #include 了这些模块的类型
        PublicDependencyModuleNames.AddRange(new string[]
        {
            "Core",              // 基础容器/数学
            "CoreUObject",       // UObject/反射
            "Engine",            // UCurveTable / FScalableFloat 所在
            "GameplayAbilities", // UGameplayAbility / UGameplayEffect
            "GameplayTags",      // FGameplayTag
            "Dura",              // ★ 项目运行时模块：要读 UDuraDamageGameplayAbility、UAbilityInfo 等
            "EditorSubsystem"    // UEditorSubsystem 基类
        });

        // 私有依赖：只在 .cpp 里用到的模块
        PrivateDependencyModuleNames.AddRange(new string[]
        {
            "UnrealEd",               // GEditor、UAssetEditorSubsystem
            "Slate", "SlateCore",     // 界面框架
            "InputCore",
            "ToolMenus",              // 编辑器菜单/工具栏扩展 API
            "WorkspaceMenuStructure", // 窗口菜单的分组目录
            "ContentBrowser",         // "在内容浏览器中定位"
            "AssetRegistry",          // 枚举/查询资产
            "EditorStyle"             // FAppStyle 编辑器样式
        });
    }
}
```

> **踩坑记录**：第一版漏了 `"EditorSubsystem"`，链接时报 `LNK2019: 无法解析的外部符号 Z_Construct_UClass_UEditorSubsystem`。看到"dllimport 的 UEditorSubsystem 符号无法解析"，第一反应就该是 Build.cs 少依赖。**UE 的链接错误很多其实是 Build.cs 问题**。

**Public vs Private 的判断标准**：如果 `.h` 头文件里 include 了某模块的头 → 该模块放 Public；只在自己的 `.cpp` 里 include → 放 Private。放 Private 能加快依赖者的编译。

### 2.3 写模块入口 DuraEditor.h / DuraEditor.cpp

每个模块都要有一个实现 `IModuleInterface` 的类，它是模块的"开机自检"：

```cpp
// DuraEditor.h
class FGasValidatorEditorModule : public IModuleInterface
{
public:
    virtual void StartupModule() override;   // 编辑器加载模块时调用
    virtual void ShutdownModule() override;  // 卸载时调用（要清理注册的东西）
private:
    void RegisterMenus();
    TSharedRef<SDockTab> SpawnValidatorTab(const FSpawnTabArgs& Args);
};

extern const FName GasValidatorTabName;

// DuraEditor.cpp 最后一行：把类和模块名绑在一起
IMPLEMENT_MODULE(FGasValidatorEditorModule, DuraEditor)
```

`StartupModule()` 里干了两件事：

```cpp
void FGasValidatorEditorModule::StartupModule()
{
    // ① 注册 Nomad 标签页（独立工具页）
    FGlobalTabmanager::Get()->RegisterNomadTabSpawner(GasValidatorTabName,
        FOnSpawnTab::CreateRaw(this, &FGasValidatorEditorModule::SpawnValidatorTab))
        .SetDisplayName(FText::FromString(TEXT("GAS 配置校验器")))
        .SetGroup(WorkspaceMenu::GetMenuStructure().GetToolsCategory());

    // ② 等菜单系统就绪后再挂工具栏按钮
    UToolMenus::RegisterStartupCallback(
        FSimpleMulticastDelegate::FDelegate::CreateRaw(this, &FGasValidatorEditorModule::RegisterMenus));
}
```

**为什么要 `RegisterStartupCallback` 而不直接在 StartupModule 里加按钮？** 因为模块加载的时机比菜单系统初始化更早，直接加会找不到 `LevelEditor.Toolbar` 这个菜单。`RegisterStartupCallback` 的意思是"等 ToolMenus 初始化完成后再回调我"。

**Nomad 标签页是什么**：不依附于某个关卡/资产的独立工具页（对比：蓝图编辑器里的页面依附于蓝图资产）。注册后它**自动出现在编辑器的 窗口 菜单里**，不需要自己再写菜单项。

`ShutdownModule()` 与之对称地清理（不清理的话热重载/退出时会崩）：

```cpp
void FGasValidatorEditorModule::ShutdownModule()
{
    UToolMenus::UnRegisterStartupCallback(this);
    UToolMenus::UnregisterOwner(this);
    FGlobalTabmanager::Get()->UnregisterNomadTabSpawner(GasValidatorTabName);
}
```

工具栏按钮的挂载（`RegisterMenus`）：

```cpp
void FGasValidatorEditorModule::RegisterMenus()
{
    FToolMenuOwnerScoped OwnerScoped(this);

    UToolMenu* ToolbarMenu = UToolMenus::Get()->ExtendMenu(TEXT("LevelEditor.Toolbar"));
    FToolMenuSection& Section = ToolbarMenu->AddSection(TEXT("DuraGASTools"));
    Section.Label = FText::FromString(TEXT("Dura 工具"));

    Section.AddEntry(FToolMenuEntry::InitToolBarButton(
        TEXT("GASValidator"),
        FUIAction(FExecuteAction::CreateLambda([]()
        {
            FGlobalTabmanager::Get()->TryInvokeTab(GasValidatorTabName);  // 点按钮 = 打开标签页
        })),
        FText::FromString(TEXT("GAS 校验")),           // 按钮文字
        FText::FromString(TEXT("打开 GAS 配置校验器…")), // 悬停提示
        FSlateIcon(FAppStyle::GetAppStyleSetName(), TEXT("ClassIcon.DataAsset")))); // 图标
}
```

> **踩坑记录**：UE 5.8 里 `InitToolBarButton` 的图标参数类型是 `TAttribute<FSlateIcon>`，不再接受老教程里的 `FSlateBrush*`。传 `FAppStyle::GetBrush(...)` 会报一长串 `Attribute.h` 的 static_cast 错误。**UE 升级后老教程的编辑器扩展代码经常有这类 API 变动，编译器报错指向引擎深处时，去引擎源码里搜一下函数签名（`Engine\Source\Developer\ToolMenus\Public\ToolMenuEntry.h`）是最快的解法。**

## 3. 编译入口

项目里已有现成脚本 `tools/Build_DuraEditor.bat`（本工具之前就存在，正好复用）：

```bat
"%UE_ROOT%\Engine\Build\BatchFiles\Build.bat" DuraEditor Win64 Development -project="%PROJECT_ROOT%\Dura.uproject" -WaitMutex %*
```

用法（在项目根目录）：

```
tools\Build_DuraEditor.bat
```

它会编译 `DuraEditor` 这个 Target（编辑器形态）。新模块第一次编译会连带编译依赖，大约 30 秒；之后增量编译只要几秒。

**注意**：UE 编辑器开着的时候 DLL 被锁住，编译会失败。先关编辑器再编译（或者用编辑器里的 Live Coding，但新建模块/新 UCLASS 这种大改动建议老老实实关掉重编）。

## 4. 骨架完成时的验证点

模块骨架搭完、还没有任何界面时，可以先验证三件事（我们当时就是这么做的）：

1. `tools\Build_DuraEditor.bat` 编译通过
2. 打开编辑器，窗口菜单里出现「GAS 配置校验器」
3. 主工具栏出现「GAS 校验」按钮，点击后弹出一个空白标签页

三件事都过了，说明：模块被正确加载、菜单扩展生效、标签页机制工作正常。剩下的就是往这个空壳里填"校验逻辑"（第 3 篇）和"界面"（第 4 篇）。
