# 03 - 校验核心逻辑实现

> 「制作过程」第 3 篇：工具的心脏 `GasValidatorCore.cpp`。讲清楚五步流水线怎么设计的，以及三个最有技术含量的坑：怎么读蓝图数据、怎么读 protected 成员、怎么正确求值曲线。

---

## 1. 核心思路：读 CDO，而不是"打开"资产

一个关键认知：**蓝图上的默认值，就存在它的 CDO（Class Default Object，类默认对象）里**。

你在编辑器里打开 GA_FireBolt 蓝图，Class Defaults 面板看到的 Cost GE、DamageType、Damage 曲线……全部存在 `GA_FireBolt_C` 这个类的 CDO 上。所以校验器不需要"打开"任何编辑器，只要：

```
AssetRegistry 枚举资产 → 加载蓝图对象 → 拿 GeneratedClass → GetDefaultObject() 得到 CDO → 读属性
```

```cpp
// 从资产注册表拿到 FAssetData 后
UObject* Loaded = AssetData.GetAsset();              // 加载资产（UBlueprint 对象）
UBlueprint* Blueprint = Cast<UBlueprint>(Loaded);
UClass* GeneratedClass = Blueprint->GeneratedClass;   // 蓝图生成的类，如 GA_FireBolt_C
const UGameplayAbility* CDO = Cast<UGameplayAbility>(GeneratedClass->GetDefaultObject());
// CDO 上就能读到配置 —— 和你在蓝图 Class Defaults 里看到的一样
```

58 个资产全部同步加载 + 扫描，实测 **0.4 秒**，完全不需要异步。

## 2. 五步流水线

`RunValidation()` 的结构是一条五步流水线，顺序很重要：

```
第 0 步  收集清单    AssetRegistry 枚举 /Game/Blueprints/AbilitySystem 下所有资产
第 1 步  加载分组    逐个加载，按类型分四组：GA 蓝图 / GE 蓝图 / UAbilityInfo / UCharacterClassInfo
第 2 步  扫 GA      同时建立"交叉引用表"：哪个 GE 被谁用作 Cost / Cooldown / Damage
第 3 步  扫数据资产  DA_AbilityInfo / DA_CharacterClassInfo，同时记录哪些 GA 被登记过
第 4 步  扫 GE      用第 2 步建立的交叉引用表做"身份判定"（这个 GE 是不是冷却 GE？）
第 5 步  反向检查    哪些玩家技能没登记进数据资产
```

**为什么需要交叉引用表？** 因为 GE 的很多规则要看"它被怎么用"：

- `GE_Cooldown_FireBolt` 这条规则——"冷却 GE 必须授予 Tag"——只有知道它被某个 GA 用作 Cooldown GE 才有意义。裸看一个 GE 是没法知道自己是干嘛的。
- 所以第 2 步扫 GA 时顺手记三张表：`GEUsedAsCooldown`、`GEUsedAsCost`、`GEUsedAsDamage`（GE 类路径 → 使用它的 GA 名字列表）。第 4 步扫 GE 时查表。

这个"先扫使用者、再扫被使用者"的顺序是整个设计的骨架。**跨资产规则永远要先建立引用图。**

## 3. 项目自定义类的 protected 成员怎么读

`UDuraDamageGameplayAbility` 的三个核心属性全是 `protected`：

```cpp
protected:
    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
    TSubclassOf<UGameplayEffect> DamageEffectClass;   // 伤害 GE

    UPROPERTY(EditDefaultsOnly, Category = "Damage")
    FGameplayTag DamageType;                          // 伤害类型标签

    UPROPERTY(EditDefaultsOnly, Category = "Damage")
    FScalableFloat Damage;                            // 伤害数值
```

外部模块直接访问 `DamageGA->DamageEffectClass` → 编译报错 C2248（访问 protected 被拒）。

两条路：

1. **改 Dura 源码把它们改成 public** —— 能用，但工具对游戏代码产生了侵入，以后同步课程更新会冲突。
2. **反射读取** —— UPROPERTY 不管什么访问级别，反射数据都是完整的，UEditorSubsystem 等引擎工具自己就这么干。

我们选了反射。三个小助手函数（都在 `GasValidatorCore.cpp` 顶部）：

```cpp
/** 读对象上的 protected TSubclassOf 属性（如 DamageEffectClass）。找不到时返回 nullptr，规则自动跳过 */
static UClass* ReadClassProperty(const UObject* Obj, const FName PropName)
{
    const FClassProperty* Prop = FindFProperty<FClassProperty>(Obj->GetClass(), PropName);
    return Prop ? *Prop->ContainerPtrToValuePtr<UClass*>(Obj) : nullptr;
}

static const FGameplayTag* ReadTagProperty(const UObject* Obj, const FName PropName)
{
    const FStructProperty* Prop = FindFProperty<FStructProperty>(Obj->GetClass(), PropName);
    return Prop ? Prop->ContainerPtrToValuePtr<FGameplayTag>(Obj) : nullptr;
}

static const FScalableFloat* ReadScalableFloatProperty(const UObject* Obj, const FName PropName)
{
    const FStructProperty* Prop = FindFProperty<FStructProperty>(Obj->GetClass(), PropName);
    return Prop ? Prop->ContainerPtrToValuePtr<FScalableFloat>(Obj) : nullptr;
}
```

要点：

- `FindFProperty` 在对象的**实际类**（蓝图生成类）上找属性——继承来的 protected 属性也能找到；
- `ContainerPtrToValuePtr<T>(Obj)` 按属性在内存里的真实偏移取值，等价于 `((T*)((&Obj) + offset))`，这是安全的，因为偏移来自反射元数据；
- 所有调用都做了空指针保护：万一未来引擎/项目改了属性名，工具**安静地跳过这条规则**，而不是崩溃或误报。

引擎自己的 protected 成员同理。比如 `FGameplayEffectModifierMagnitude::ScalableFloatMagnitude` 在 5.8 里是 protected（旧版有 public getter，5.8 没有），我们同样用反射读：

```cpp
static const FScalableFloat* GetScalableFloatFromMagnitude(const FGameplayEffectModifierMagnitude& Magnitude)
{
    static FStructProperty* Prop = FindFProperty<FStructProperty>(
        FGameplayEffectModifierMagnitude::StaticStruct(), FName(TEXT("ScalableFloatMagnitude")));
    if (Prop == nullptr) return nullptr;
    return Prop->ContainerPtrToValuePtr<FScalableFloat>(&Magnitude);
}
```

> **踩坑记录**：写这段之前先翻了引擎源码（`D:\UE\UE_5.8\Engine\Plugins\Runtime\GameplayAbilities\Source\GameplayAbilities\Public\GameplayEffect.h`）确认 5.8 的成员布局——5.8 删掉了 `GetScalableFloatMagnitude()`，只留 protected 成员。**对着本地引擎源码写扩展代码，比对着网上教程写靠谱一个版本号。**

## 4. FScalableFloat 数值的正确求值姿势

蓝耗/伤害/冷却时长都存在 `FScalableFloat` 里，它的语义是：

```
最终值 = Value × 曲线表(RowName).Eval(Level)
```

没配曲线就是常量 `Value`。求值实现：

```cpp
float EvaluateScalableFloatAtLevel(const FScalableFloat& ScalableFloat, float Level)
{
    if (ScalableFloat.Curve.IsNull() || ScalableFloat.Curve.CurveTable == nullptr)
    {
        return ScalableFloat.Value;
    }
    const FRealCurve* Curve = ScalableFloat.Curve.GetCurve(TEXT("GASValidator"), false);
    return Curve ? ScalableFloat.Value * Curve->Eval(Level) : ScalableFloat.Value;
}
```

> **踩坑记录（本项目最典型的一个）**：最初用引擎的 `GetStaticMagnitudeIfPossible(1.f, Out)` 求值，结果给 4 个正常配置的 Cost GE 全部报了"蓝耗为 0"的误报。排查过程：
> 1. 先怀疑求值 API 在 5.8 行为变了 → 换成上面的手工求值，还是报；
> 2. 加调试日志打印：`Value=-1.0, Row=FireBolt, Eval(1)=2.5, 最终=-2.5` → **数值根本不是 0，是负数**；
> 3. 查项目代码发现所有技能都写 `FMath::Abs(GetManaCost(Level))` —— **这个项目的蓝耗按 GAS 惯例存成负数，游戏侧取绝对值**。
>
> 结论：不是求值错了，是**规则写错了**——判定条件应该用 `FMath::IsNearlyZero(FMath::Abs(CostValue))` 而不是 `<= 0`。修正后 4 条误报全部消失。
>
> 这件事的教训：**工具报错之前，先确认自己理解了项目的约定**。负数蓝耗、运行时赋值的 InputTag，这些都是"读代码读不出来、要看使用方"的隐性约定（详见第 5 篇误报治理）。

## 5. 敌人技能 / 被动技能的差异化判定

同一条"没配冷却"规则，对玩家技能是警告、对敌人技能只是提示——敌人普攻本来就不需要冷却。判定逻辑：

```cpp
const bool bEnemy   = IsEnemyAsset(PackagePath);      // 路径包含 /Enemy/
const bool bPassive = IsPassivePath(PackagePath)      // 路径包含 Passive
                   || GACDO->IsA<UDuraPassiveAbility>(); // 或继承 C++ 被动基类
```

- 目录约定（`/Enemy/`、`PassiveSpells/`）是**这个项目的资产组织约定**，工具直接利用它，不需要额外标记；
- `IsA<UDuraPassiveAbility>()` 是类型判断兜底，防止有人把被动技能放错目录；
- 成本检查更严格：只有"非被动且非敌人"的 GA 缺 Cost GE 才警告。

**工具的提示强度应该匹配实际意图**——把"合理设计"报成"错误"，是最快失去用户信任的方式。

## 6. DA_AbilityInfo 的交叉校验

DA_AbilityInfo 是技能菜单的数据源，每条 `FDuraAbilityInfo` 有：AbilityTag、CooldownTag、Icon、LevelRequirement、Ability。

这里最有价值的规则是 **CooldownTag 与冷却 GE 的一致性**（跨三个资产的链式检查）：

```
DA 条目.CooldownTag  ←对比→  条目.Ability 的 CDO → GetCooldownGameplayEffect() → GetGrantedTags()
```

```cpp
const UGameplayAbility* EntryGA = Entry.Ability->GetDefaultObject<UGameplayAbility>();
const UGameplayEffect* CooldownGE = EntryGA->GetCooldownGameplayEffect();
const FGameplayTagContainer& GrantedTags = CooldownGE->GetGrantedTags();

if (Entry.CooldownTag.IsValid() && !GrantedTags.HasTagExact(Entry.CooldownTag))
{
    // 警告：填的标签和冷却 GE 实际授予的对不上
    // 后果：技能菜单靠这个标签监听冷却结束，对不上 = 冷却显示永远不刷新
}
```

为什么要查这么深？因为技能菜单刷新冷却的原理是：**监听"CooldownTag 从 ASC 上被移除"这个事件**。链条上任何一环（GA 没配冷却 GE → 冷却 GE 没授予 Tag → DA 填错 Tag）断了，现象都是"冷却永不恢复"。工具把链条上每一环都单独检查，报错信息直接指向该修的那一环。

另外两处数据资产检查：

- **重复 AbilityTag**：`TMap<FString, int32>` 记录"标签→首次出现位置"，第二次出现时报错（查询永远命中第一条，第二条是死数据）；
- **反向登记检查**（第 5 步）：把 DA 和 DA_CharacterClassInfo 引用过的 GA 类路径收进 `RegisteredAbilityPaths` 集合，最后遍历所有玩家主动技能，不在集合里的报提示"没登记进技能菜单数据源"。

## 7. 结果排序与统计

扫描产出 `TArray<FGasValidationIssue>`，最后统一排序：**错误 → 警告 → 提示，同类内按资产名**。用户打开面板第一眼看到的一定是最严重的问题。

```cpp
Issues.Sort([](const FGasValidationIssue& A, const FGasValidationIssue& B)
{
    if (A.Severity != B.Severity) return A.Severity < B.Severity;  // 枚举顺序 = 严重度顺序
    if (A.Category != B.Category) return A.Category < B.Category;
    return A.AssetName < B.AssetName;
});
```

`FGasValidationResult::Recount()` 统计三级数量，面板顶部的统计行直接用。

## 8. 每条规则的三要素

写每条规则时固定回答三个问题（这也是文档第 8 篇逐条精讲的模板）：

1. **查什么**：读哪个资产的哪个属性？
2. **为什么**：违反了会出什么运行时 bug？（报错文案里必须用人话讲出来）
3. **在哪修**：提示文案要指到蓝图里的具体属性名，比如"在蓝图 Class Defaults 的 Cooldown Gameplay Effect Class 里指定 GE_Cooldown_xxx"。
